# ZeoSyn V2 修改方案

日期：2026-10-09。状态：**方案，未实施，未运行**。V1 协议见 [ZEOSYN_V1.md](ZEOSYN_V1.md)，V1 结果见 `results/zeosyn_direct_v1_local_20261008/`。

## 目标

- **H1**：Agent 相对公开 D0 有提升。V1 已经观察到：+0.54 个百分点，95% 区间 [0.38, 0.71]。
- **H2（主假设）**：KG 相对 Agent 有提升。
- **H3（次要）**：KG 相对 RAG 有提升。RAG 只作辅助对照。

## 一、V1 为什么 KG 没有超过 Agent

V1 测试集上各组相对 D0 的增益：Agent +0.54，RAG +0.10，KG+RAG +0.17 个百分点。RAG−Agent 和 KG−Agent 的区间都不跨 0。
在训练集内部划出的开发集上复查（只用于诊断，RF 减为 60 棵树、3 个 seed），排序相同：Agent +0.09，KG+RAG −0.32，RAG −0.43。因此 Agent 胜出是稳定现象，不是偶然。

原因（均可在 `results/zeosyn_direct_v1_local_20261008/` 的原始记录中核对）：

1. **固定检索词决定了话题，知识组的提案被带着走**。每轮所有 20 条知识组轨迹都收敛到同一类公式：第 1 轮是阳离子/Al 电荷平衡，第 2 轮是 `F/sda1`，第 3 轮是 Arrhenius 型的时间-温度项。第 2 轮里，20 条轨迹**全部**引用了同一段关于 HF/OSDA 比的检索文本。Agent 不受话题限制，主要提出碱度 `OH/T`、水量 `H2O/T` 和 OSDA 电荷密度。
2. **检索质量低**。例如第 1 轮的 9 条 RAG 结果中，只有约 3 条与 OSDA 结构导向直接相关；其余是加氢裂化、活性炭吸附、羰基化反应和作者信息页眉。
3. **KG 的图结构对模型不可见**。提示词里 KG 证据只显示为两个哈希 ID（`kg-node-…>kg-node-…`），没有节点名称和关系类型。KG 条目本身多是孤立的句子片段，KG 的 15 种关系也都是通用类型（如 `EXPERIMENT_USES_MATERIAL`）。
4. **提示词要求知识组“依据证据提出假设”**。模型因此按检索到的内容构造描述符，而不是按自己判断最重要的因素。知识组把 18–20/30 个提案标为“新组合”，Agent 只有 9/30。证据使提示词变长到约 4 倍，但推理 token 数没有变化（约 460）。
5. **根本原因**：新描述符只能重组已有的凝胶和 OSDA 输入，提升上限约 1 个百分点。凝胶化学规律又是模型已知的教科书知识。外部知识没有提供模型缺少的信息，就只能起干扰作用。

结论：要让 KG 有机会超过 Agent，必须同时做到两点：(a) 修正知识的提供方式；(b) 给 KG 一个真正的信息通道，即 Agent 凭记忆做不到的跨文献汇总。

| 改进项 | 对应的 V1 问题 | 是否必须 | 位置 |

| 模型自主决定检索内容 | 原因 1 | 必须 | C1 |
| KG 以可读形式呈现（名称、关系、论文数） | 原因 3 | 必须 | C3 |

| 检索质量过滤与审计 | 原因 2 | 必须 | D |

## 三、完整方案

### A. 实验规范

- **A1 预注册文档**：写明 H1–H3、主指标、fit seed、每组轨迹数、对照组、判定标准（KG−Agent 的 95% 区间下限 > 0），以及开发集上最多迭代几轮。在正式评估之前提交，并记录 commit hash。
- **A2 开发集工具**：在训练集内部按 DOI 划出固定的开发验证集。评估命令增加 `--split dev|test` 参数，`test` 只有在协议冻结后才能运行。
- **A3 V1 结果文档**：把第一节的内容写成负结果加机制分析，作为论文中的消融实验。
- **A4 迭代日志**：开发集上的每次修改都记录改了什么、为什么改、开发集结果如何。

### B. KG 合成知识层（信息通道）

- **B1 可行性探测【关卡 1】**：在 KG 中识别合成实验用到的 OSDA，与 ZeoSyn 的 OSDA 名称、IUPAC 名、同义词匹配；把产物名称对应到 IZA 代码（名称到代码的对照表用训练集的 `product1` → `Code1` 生成）。统计训练集配方的覆盖率，并检查 KG 论文有没有年份。**覆盖率 ≥ 40% 才继续。**
- **B2 实体链接模块**：OSDA 规范化（名称、同义词、SMILES），产物名称到 IZA 代码的映射。
- **B3 KG 合成表**：每个合成实验一行，字段包括论文、年份、OSDA、产物框架，以及能解析出的条件（Si/Al、F、OH、H₂O、温度、时间、杂原子）。
- **B4 文献特征库**：预先固定一份通用的特征清单，不根据测试结果挑选。例如：该 OSDA 的报道次数和论文数、最常见框架及其占比、结果熵、小/中/大/超大孔框架的占比、文献中报道的 Si/Al 和 F/OH 中位数。防泄漏规则：
  - 每条配方排除它自己所在的论文（训练行同样排除，否则训练时特征“太准”）；
  - 测试论文全部排除；
  - 另做一个时间截断版本：只用比该配方论文更早发表的文献。
- **B5 打乱版特征库**：固定随机种子，打乱 OSDA 与实验之间的对应关系，保持特征分布不变。
- **B6 直接答案审计**：统计有多少测试配方的“OSDA–框架组合”在非测试论文中被报道过，在论文中如实披露。
- **B7 单元测试**：检查本文排除、测试论文排除和时间截断都确实生效，打乱版的分布与原版一致。

### C. 生成流程改造

- **C1 统一的三步流程（所有组都一样）**：
  1. 模型自主选择本轮要研究的合成因素，并写出不超过 2 个检索问题；
  2. 系统按问题检索证据（Agent 组跳过这一步）；
  3. 模型提出描述符。

  各组的 LLM 调用次数相同，KG 和 RAG 的证据 token 预算相同。V1 那种由固定检索词决定每轮话题的做法取消。
- **C2 Agent 组**：同样的流程，没有检索。
- **C3 KG 证据呈现**：按模型的问题，从 B3 合成表和 KG 中取出汇总事实，用实体名称、关系类型和支持论文数来表述，例如“TMAda⁺ + F⁻, Si/Al = ∞ → CHA（7 篇论文）”。不再显示哈希 ID 和孤立的句子片段。
- **C4 KG 组的输入目录**：额外列出 B4 的文献特征及其含义，公式可以引用。
- **C5 提示词调整**：所有组都改为“证据只在能补充你自身知识时使用，不要因为某段文字提到了就据此构造描述符”。
- **C6 沿用 V1 的规则**：3 轮、每轮 1 个描述符、不给标签反馈、技术修复最多 1 次、失败的槽位保留不补。
- **C7 完整记录**：每轮的研究因素、检索问题、返回的证据，以及描述符用到了哪些 KG 特征。

### D. 检索质量

- **D1 RAG 过滤**：只保留实验部分和合成相关的文本块，排除催化、吸附、BET 等无关内容。
- **D2 KG 查询方式**：改为基于实体链接的查询（按 OSDA、框架、条件查找），不再用词面匹配种子节点加两跳扩展。
- **D3 检索审计**：在开发集的问题上评估相关率，目标 ≥ 70%。
- **D4 测试论文排除**：沿用 V1 的 fail-closed 机制，同时覆盖 RAG、KG 证据和 B4 特征库。

### E. 实验组

| 组 | 作用 | 是否必须 |
|---|---|---|
| E1 Agent | 验证 H1，作为 H2 的比较基准 | 必须 |
| E2 KG（证据 + 文献特征） | 验证主假设 H2 | 必须 |
| E3 RAG | 辅助，验证 H3 | 建议 |
| E4 打乱 KG | 证明提升来自正确的知识，而不是多了几列特征 | 必须 |
| E5 只加文献特征、不用 LLM | 诊断：LLM 的选择和组合有没有额外价值 | 建议（不调用 LLM） |
| E6 相同事实平铺 | 只在要声称“图结构本身有用”时才需要 | 可选 |

每组 10 条轨迹；如果开发集上噪声偏大，提高到 15 条。

### F. 评估与分析

- **F1 主指标**：准确率或 macro-F1，二选一，在 A1 中确定。
- **F2 统计方法**：以轨迹为统计单位，seed 内先平均；用 bootstrap 计算 KG−Agent 的区间，按 A1 的判定标准下结论。
- **F3 机制分析**：
  - 按“该配方的 OSDA 在 KG 中有没有覆盖”分层，提升应主要集中在有覆盖的配方上；
  - 按“该 OSDA 在训练集中是否常见”分层，KG 对少见 OSDA 的帮助应更大。
- **F4 敏感性分析**：时间截断版特征、只用不在 ZeoSyn 里的论文构建的 KG、macro-F1、换用 HGB 预测模型。
- **F5 假设质量**：自动检查引用的 KG 事实是否真实存在，统计描述符使用 KG 特征的比例。

### G. 运行基础设施

- **G1 本地运行脚本**：正式提供台式机运行脚本，替代 Slurm，支持并行生成、断点续跑和完整日志，并收编 V1 时自行编写的 `run_local.py`。
- **G2 内存检查**：载入知识库的步骤先在台式机上实测峰值内存。
- **G3 结果回收**：沿用 collect 流程，统一写入 `results/` 再推送。
- **G4 `AGENTS.md`**：增加台式机运行流程。

### H. 投稿前的后续工作（本轮不做）

- 不用领域知识的 LLM 特征工程 baseline（CAAFE、LLM-FE）；
- 第二个 benchmark（OCM）；
- Small / Medium / Large KG 的规模对比。

## 四、执行顺序与关卡

| 步骤 | 内容 | 在哪里做 | 预计时间 |
|---|---|---|---|
| 1 | A1–A2、G1 | 这里写代码 | 约 2 天 |
| 2 | B1 可行性探测 → **关卡 1**：覆盖率 < 40% 就停下，重新考虑方案 | 台式机运行 | 1–2 天 |
| 3 | B2–B7、C、D、E | 这里写代码，台式机构建知识层 | 1–1.5 周 |
| 4 | 开发集迭代，最多 3 轮 → **关卡 2**：开发集上 KG 不优于 Agent，就不做正式评估，如实报告 | 台式机运行 | 2–3 天 |
| 5 | 冻结协议，在 V1 的测试集上做唯一一次正式评估，然后分析、写作 | 台式机运行 | 1–2 天 |

总计约 2.5–3 周。

## 五、风险

- **关卡 1 是最大的不确定性**：KG 是从论文自由文本里抽取的，OSDA 和产物能否可靠地对应上，现在还不知道。
- **不能保证 KG > Agent**：这套设计能让这个假设得到公平的检验，并且在它成立时足以说服审稿人。但如果打乱 KG 组也有同样的提升，或者 KG 没有超过 Agent，都必须如实报告。V1 的结果也照原样保留和报告。

4. 每组 10 条还是 15 条轨迹。
